# Design

## Context

动机见 `proposal.md`。塑造方案的现状与约束：

- **两处同源缺口**：`RemoteAtomicBase` 的标量族与有值引用族各有一处 `resp = answer.getAtomicOpResponse();`，**均在 `try` 内、随后即用 `resp.getStatus()` 裁决**，中间无 presence 判定。两处结构逐字对称——只修一处会留下同类洞。
- **该族已在用 presence 判定**：有值引用族读载荷时用的是 `resp.hasOldValueBytes()` / `resp.hasValueBytes()`。缺的不是"presence 判定的习惯"，而是**信封层这一处**。
- **既有判例（队列）**：`OBlockingQueue API` 的缺码形条款（W10 立）把缺码形按**瞬态失败**处置——"退避、重取路由、重发"，明确"MUST NOT 读取 protobuf 默认实例"，理由写得极具体：默认实例 `status` 为枚举零值 `OK`，会被误判为"成功空应答"致 `take` 交付零长度元素、`size` 读回 0。
- **可重试通道既存**：该族契约已规定"可重试失败时写操作以**同一 `op_seq`** 自动重发至请求总超时界限——去重槽保证重发不重复生效"。
- **该族另有跨会话严格守卫**：`writeOp && route.session().sessionId() != startSession` 时显式抛 `SESSION_EXPIRED`（"dedup slot no longer applies"）。本条**不触碰**它。

## Goals / Non-Goals

**Goals:**

- 让"缺码形应答"在该族**不可能**被读作成功：不返回 0、不假成功。
- 复用既有可重试通道，不新增机制、不新增配置。

**Non-Goals:**

- 不放宽跨会话换代守卫（`SESSION_EXPIRED` 语义不变）。
- 不改其余状态码（`NOT_LEADER`/`OVERLOADED`/`INVALID_REQUEST` 等）的既有裁决。
- 不动其余三族的同型缺口（本次只登记）。

## Decisions

### D1 缺码形按**可重试失败**处置，而非直接抛错

沿队列判例。理由：缺码形意味着本请求**未被正常处理**（拒绝路径组装违例或应答串号），重发安全且能自愈；直接抛错会把一次可自愈的异常变成用户可见失败。失败的最终收口仍是**显式**的（预算内不可判定 → `OpenLatchTimeoutException`），不静默。

**备选与否决**：直接抛 `OpenLatchException` → 否决：与队列判例不一致，且把可自愈形态降级为硬失败。

### D2 复用既有 `op_seq` 重发通道，不新增机制

写操作重发由服务端去重槽保证不重复生效（契约既有）；读类重发天然幂等。**跨会话**仍由既有严格守卫裁决——本条的 `continue` 走的是同一循环，"路由已换会话"仍会在下一轮撞上该守卫并显式抛出。**不因本条放宽任何既有限制。**

### D3 两处一并覆盖（标量族 + 有值引用族）

两处结构逐字对称、缺口同源；只修一处是最典型的"修了一半"。这条也算一条证据：缺口的形状（同一个 `getAtomicOpResponse()` 直读）说明它是复制出来的，不是权衡出来的。

### D4 只堵"默认实例"这一条，不做额外收紧

判定条件是 `!answer.hasAtomicOpResponse()`，触发面极窄（正常服务端**必填**该 oneof，既有单测与 E2E 全绿可证）。不做"状态码非 OK 即重试"之类的扩大化——那会改变既有拒绝语义。

### D5 其余三族不动，登记在册

`RemoteCountDownLatch` / `RemoteBarrier` / `RemoteTopic` 同样缺少该判定（已逐一核实）。但：它们**没有观测证据**，且一次改动多处**写路径**会让归因变难（今天刚吃过这个教训）。故本次登记在册，附核实结论与代码位置。

## Risks / Trade-offs

- [重发可能掩盖服务端真缺陷] → 缺码形本身即异常输入；重发失败最终以**显式超时**收场，不静默。且该形态在正常服务端不可达（oneof 必填）。
- [写路径重发导致双生效] → 同 `op_seq` + 服务端去重槽，契约既有保证；跨会话仍被严格守卫拦下。
- [误伤正常应答] → 判定条件是 presence 缺失，正常应答必填；既有原子族单测与 IT 全绿即为回归底线。
- [只修一族、留下同型洞] → 已显式登记，并在本设计中写明三族位置，便于后续一次性收口。

## Migration Plan

纯客户端变更：无 proto 变更、无配置项、无状态迁移。服务端零改动。回滚=还原客户端产物。
