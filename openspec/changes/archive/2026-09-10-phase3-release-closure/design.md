# Design: phase3-release-closure

## Context

动机与缺口清单见 proposal.md「Why」，不赘述。本设计只交代收口动作的**口径与边界**，以及塑造它们的现状事实：

- Phase 3 四个 T 变更均已归档，验收证据在实施期已采集并随档（`t1/t2/t3/t4-acceptance-evidence.md`、`evidence/` 目录），构建记录与演练报告在 `docs/`。
- 详设 `docs/OpenLatch-Phase3-详细设计说明书.md` 的实现期勘误**已回写正文**（§2.1、§3.3、§3.4、§4.2、§4.3、§5、§10.4 各有"实施勘误"块），仅版本/状态/修订记录未收口。
- Phase 1/2 收口先例：`docs/Phase1-验收报告.md`、`docs/Phase2-验收报告.md`（含 §验收项逐项闭环 + DoD 五条自检 + 基准汇总 + 缺陷/遗留 + 发布宣告尾注）；`phase2-release-closure` change 是唯一的阶段收口 change 样板。
- 仓库纪律：Maven 一律 `-s /home/lam/repo/settings.xml`；`-Pdrill` 进程级演练与需 TTY 的手工安全走查在无 TTY 沙箱不可靠，留 CI/运维环境（`t4-acceptance-evidence.md` 已如实标注）。

## Goals / Non-Goals

**Goals:**

- 产出 `docs/Phase3-验收报告.md`，把总体计划 §5.3 六项 + 详设 §8 六项 + DoD §5.4 五条逐项闭合成可追溯证据文档。
- 复跑基准，产出 Phase 3 基线与 Phase 1 基线的对比记录。
- 收口详设版本/状态、README 文档面，回填 T4 记账，使仓库文档面与已交付事实一致。
- 本 change 归档提交即 **Phase 3 发布宣告**（沿 P2-19/P3-17"归档即发布"先例）。

**Non-Goals:**

- 不改任何产品代码、协议、公开 API 与测试缺省语义（零行为变更）。
- 不复改详设各章已回写的勘误正文（避免引入语义变更）。
- 不新建集群档认证夹具（见 D1）。
- 不做 `-Pdrill` 进程级演练与需 TTY 的手工安全走查（环境限制，留 CI/运维）。
- 不触碰 §9 遗留项（控制台写操作、读者批量授予、多租户、客户端按 key 指标等）。

## Decisions

**D1：集群档认证零副作用夹具（T4 tasks 3.6 的实证）拆为后续独立小变更，本变更不做。**

- 现状：未认证 HELLO 零 `SESSION_OPEN` 副作用由"门闩分叉置于 `cluster.sessionCoordinator().handleHello` 之前"的结构保证 + 单机档零副作用用例锁定；要集群档实证需新建三节点 `OpenLatchServer` 夹具（`ClusterHarness` 直驱 `ClusterRuntime`、不经 `ServerSessionHandler` 门闩）。
- 备选一（折入本变更）：会把新的集群测试装配引入一个本该零产品语义变更、可一次性归档的收口变更，抬高爆炸半径与验证成本，且夹具设计需独立评审。
- 备选二（不做、不记）：留空框，收口账不实。
- **定夺**：拆出。本变更在验收报告与 T4 tasks 中把 3.6 改记为"已评估·结构保证 + 单机覆盖，集群夹具另立小变更"，口径诚实且可追溯。

**D2：验收报告的证据口径 = 引用汇总，仅基准需新执行。**

- 各 T 的验收证据在实施期已采集并归档；重新执行既浪费，也会因环境漂移产生与当时不一致的数字。
- **定夺**：报告逐项列"判据 / 证据路径 / 结果"，证据路径指向已归档的 `*-acceptance-evidence.md`、演练报告、构建记录；唯一需新执行的是 DoD §5.4-5 的基准复核（D3）。

**D3：基准复核 = 复跑同一手写 harness，与 Phase 1 基线对比；不做 TLS 开启档对比。**

- 复跑 `BenchmarkMain`（`openlatch-examples`）产出 `docs/benchmark-baseline-<date>.md`，与 `benchmark-baseline-2026-08-29.md` 逐项对比。
- 不做 TLS 档：TLS 为可选路径（默认关），纳入对比会引入证书夹具与额外变量；DoD §5.4-5 只要求"与上一里程碑对比无显著退化"。
- **定夺**：单档对比；判定口径沿用 DoD 的 >20% 退化需说明原因；基准非发布门槛（README 既有声明），噪声显著时以量级一致判定并注明。

**D4：详设收口只改版本/状态/修订记录，不动已回写的勘误正文。**

- 各章勘误（§2.1/§3.3/§3.4/§4.2/§4.3/§5/§10.4）在实施期已回写，本期复改只增风险、无收益。
- **定夺**：v1.0 → v1.1，状态"待评审" → "已验收"（沿 Phase 1/2 口径），补一条修订记录指向实现期各章勘误与本次收口。

**D5：README"已知局限（Phase 1）"改判而非整节删除。**

- 该节现存四条：①读者批量授予留 Phase 3 评估；②放弃等待不主动取消排队；③单机内存锁无集群（Phase 2）；④`waitTime` 计时在客户端时钟回拨。其中 ③ 已由 Phase 2 交付、① 的评估结论属 Phase 3 范围外遗留。
- **定夺**：按现状改判——已交付项（集群等）移除或重标为已解决；仍成立项（②④、① 的读者批量授予）保留。同步更新"文档"节链接（补 Phase 2/3 详设与验收报告）。中英双版对齐。

**D6：发布宣告口径 = 本 change 归档提交即 Phase 3 发布。**

- 沿 `phase2-release-closure`（归档即发布）与 P3-17 验证列"Phase 3 发布"口径。
- **定夺**：验收报告尾注发布宣告（版本/日期/commit）；归档提交完成即发布完成。

## Risks / Trade-offs

- **[基准复跑环境噪声致数字与 Phase 1 基线不可比]** → 报告记录环境信息与判定口径；噪声显著时以量级一致判定并注明；基准非发布门槛（README 既有声明），不阻塞发布。
- **[验收报告证据链接失效/指向不存在的路径]** → 每项 verify 要求证据路径可点开存在；报告成稿后逐链接核验。
- **[详设状态改判被质疑越权]** → 改判沿 Phase 1/2 先例（作者本人签署），本 change 即签署载体；不触及契约语义。
- **[README"已知局限"改动误删仍成立条目]** → 逐条对照现状改判，仅移除已被 Phase 2/3 交付覆盖的条目；改动最小化。
- **[T4 3.6 留白被误解为已完成]** → D1 口径写入报告与 tasks，明确标注"结构保证 + 单机覆盖，集群夹具另立小变更"。
