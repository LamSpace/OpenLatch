# Proposal

## Why

`fix-lane-route-refresh` 落地后，路由**全局**可刷新（惰性共享刷新会建/换获取车道）。于是"会话换代"不再只发生在断连重连时——它可以在任何请求在途期间发生。

在此背景下核查发现一处**文字与实现的张力**：`RemoteCondition`（`CONDITION_OP_SIGNAL`）与 `RemoteTimer`（`SCHEDULE`/`DISARM`）的变异车道**没有任何跨会话换代守卫**（全族 `SESSION_EXPIRED` 命中 0 次），其重发环在观察到会话变化时会**重建信封、在新会话上续发**；而在册 W11 行明写"变异超时**跨会话放弃**（契约，`isArmed`/`isFired` 读数可核对是否已换代）"。

两者不能同时为真：

- 若实现为真 → 契约措辞过时（须回写）；
- 若契约为真 → 实现存在**静默跨会话续发**：去重槽按 `(会话, op_seq)` 记账（换会话即槽不中），续发等同新写 ⇒ 与 `fix-queue-noeffect-monotonic` 刚堵掉的**同一类静默重复生效**（对条件变量=`signal` 被搬运两次的语义等价物；对定时器=`DISARM`/`SCHEDULE` 被重放）。

> **证据状态**：该风险由**代码阅读**推得（"无守卫"是已核事实；"重复生效"是**未证**后果）。故本 change 只做一件事：**造确定性复现**。造得出 → 另立修复 change（判负/判真由实测定）；造不出 → 转证据记录（登记"该形态不可达"），归因结论回写 W11 行。

## What Changes

- 新增**确定性复现夹具**（脚本化服务面，opt-in 门控）：构造"条件/定时器变异请求在途 → 会话换代（经既有改道机械换新会话）→ 在途请求续发"的时序，断言**续发是否真的落到新会话上**（计数证据），以及是否产生**重复效果**（脚本化服务端按 `(会话, op_seq)` 记账，模拟去重槽语义：新会话槽不中即执行）。
- 夹具同时钉住**两种可能结论**：若续发成立，红=实现存在静默跨会话续发（须修）；若续发不成立（例如某处隐含守卫），则记录为"契约与实现一致、措辞待回写"的证据。
- **非目标**：不做修复（修复另立；本 change 只给判据）；不改 wire；不改服务端；不动 `fix-lane-route-refresh` 已落地的路由取用纪律。
