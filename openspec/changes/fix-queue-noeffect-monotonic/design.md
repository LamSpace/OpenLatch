# Design

## Context

动机见 `proposal.md`。以下只记录塑造方案的现状与约束。

- **判定现状**：`RemoteBlockingQueue` 的两处写循环（`parkLoop` 与 `exchange`）各自维护一个 `noEffectReject` 布尔：不确定窗（`TimeoutException`、瞬态 `ExecutionException`）置 `false`；明确零生效（`NOT_LEADER` 状态、缺码形应答）置 `true`；而**跨会话续发的放行判据只读"最近一次尝试"的取值**。
- **续发的安全前提**：服务端去重槽按 `(会话, op_seq)` 记账并原值重放（core 的 `AtomicEntry` 规则 4/5）——**换会话即槽不中**，续发等同一次新写。故"允许跨会话续发"等价于断言"此前从未有过可能已生效的尝试"。
- **明确零生效的来源**：`NOT_LEADER` 由服务端**入口角色门**在触达状态机前拒绝；缺码形为拒绝组装路径产物（既有裁决：二者均按"未入任何日志、零生效"处置）。
- **既有承诺（必须保持）**：既有场景"换主窗口写重发不双插不偷插"要求**首发即** `NOT_LEADER` 时透明改道、在新 Leader 以同 `op_seq` 续发且元素恰一次——该路径**从未进入不确定窗**，本 change MUST NOT 影响它。
- **证据状态**：本 change 要堵的洞由代码阅读推得，**尚未实证**——故 D3 设复现门槛。

## Goals / Non-Goals

**Goals:**

- 让"不确定窗"在同一逻辑写操作内**单调**：一旦进入，只能由"操作完成"结束，MUST NOT 被后续的明确拒绝覆盖。
- 把"是否放行跨会话续发"收敛为**单一、可单测**的判定点，取代两处写循环里的布尔读写。
- 把该纪律写进规格（MUST 条款 + 可执行场景），使其成为契约而非实现细节。

**Non-Goals:**

- 不做路由收敛/触发器（W11 本体归另立 change）。
- 不改缺码形与 `NOT_LEADER` 的处置语义，不改其"零生效"认定。
- **不放宽任何现存失败**：没有一条路径允许把显式失败变成静默成功。
- 不改服务端、协议、其余族。

## Decisions

### D1 不确定窗取单调语义（备选：维持逐次覆写 / 改为"一律不放行"）

**采纳**：一旦本操作有过不确定窗尝试，则后续**任何**明确零生效拒绝都不得放行跨会话续发；跨会话以显式失败收场（`SESSION_EXPIRED`/超时）。同会话重发不受影响（槽仍兜底）。

| 备选 | 否决理由 |
|---|---|
| 维持逐次覆写（现状） | 等于承认"最近一次拒绝"能证明"整段历史零生效"——逻辑上不成立，且后果是静默重复生效。 |
| 一律不放行跨会话续发 | 会打掉既有承诺（首发即 `NOT_LEADER` 的透明改道），把合法可用性一并收紧；超出本 change 的必要范围。 |

### D2 判定收敛为单一策略点（备选：两处写循环各自改）

**采纳**：把"是否允许跨会话续发"抽成一个极小的可测单元（判例：`AwaitTracker`/`HeldLockRegistry` 的可测切分），两处写循环共用。理由是这条判定将来要为其余写族复用（见 Open Questions），且判定分散在循环里**无法被单测直接覆盖**——而 D3 的复现恰好最可能在单测层面达成。

### D3 复现优先：造不出确定性复现则不落地收紧

本 change 的第一道门是造出确定性复现（策略点单测 + 可达时补端到端，见 tasks 1.x）。**造不出则停止实现**，把本 change 转为证据记录（登记"判定为不可达/需更强时序"的结论），不落地收紧。理由：本仓既有纪律是"红先"，且此处收紧的依据是推演而非观测；在没有反例的情况下收紧，等于用推测去改契约。

### D4 只收紧不放宽（兼容性锚）

实现完成后，下列既有行为 MUST 逐项不变，并以既有用例为锚：首发即 `NOT_LEADER` 的透明改道与同 `op_seq` 续发（`notLeaderRetriesSameEnvelopeSameOpSeq`）、缺码形按瞬态重发（`malformedRejectEnvelopeRetriedNeverReadAsSuccess`）、`QUEUED`→推送→同 `requestId` 重发闭环。任何一条变化都说明收紧越界。

### D5 缺码形的"零生效"认定不在本 change 内重议

缺码形被既有规格认定为"拒绝组装路径产物 = 零生效"。本 change **沿用**该认定，只改"它不得洗白更早的不确定窗"。若将来发现缺码形可能出现在"请求已生效"之后，那是另一条更硬的议题（缺码形的语义），不并入本 change。

## Risks / Trade-offs

- [复现不可达 → 无据收紧] → D3 门槛：造不出就停，转证据记录。
- [收紧误伤既有透明改道] → D4 明文锚定三条既有用例；新场景"首发即明确拒绝时透明改道不变"与之互为守卫。
- [窄窗内可用性下降] → 该窗内原行为是**静默重复生效**（不安全）；改为显式失败是净改善，与"假绿严格劣于显式失败"判据同向。
- [策略点抽取引入重构风险] → 抽取范围限于判定本身（纯函数），不搬移循环控制流；既有用例为回归底线。

## Migration Plan

纯客户端变更：无协议变更、无配置项、无状态/数据迁移。回滚＝还原客户端产物，服务端与协议无残留。

## Open Questions

- 同一纪律是否推广到原子族与其余写族（队列是当前唯一有"零生效逃逸"的族；原子族已是严格守卫、等效单调）。该项属路由收敛 change（W11 本体）的范围，本 change 不动，但其 D1 语义将作为那边的输入。
