## 1. 目的与范围

本文档在概要设计 §9 实施路线图的基础上，回答三个问题：

1. **项目需要多少阶段完成** —— 结论为 **3 个阶段**，其中 Phase 1 再细分为 4 个里程碑（M1–M4），Phase 2 细分为 4 个步骤（S1–S4），Phase 3 细分为 4 个工作项（T1–T4）；
2. **每个阶段的目标是什么** —— 每阶段/里程碑给出明确的目标、交付物与退出标准；
3. **如何验证** —— 建立"测试金字塔 + 阶段验收清单 + 完成定义（DoD）"三层验证体系，每项验收标准均可执行、可判定。

本文档不展开模块级设计，模块级设计见三份详细设计说明书（见 §8 文档清单）。里程碑之下的 **子任务拆分**（共 69 个，每个可独立交付、独立验证）见 §9 总览；子任务的完整定义（内容与交付物、前置依赖、验证）在各详细设计说明书中：《Phase1》§13、《Phase2》§13、《Phase3》§10。

## 3. 总体阶段划分

### 3.1 阶段总览

| 阶段                | 目标                                                                      | 前置依赖                           | 交付物                                          | 退出标准（摘要）                   |
|---------------------|---------------------------------------------------------------------------|------------------------------------|-------------------------------------------------|------------------------------------|
| **Phase 1（MVP）**  | 单机可用的分布式锁服务：4 种锁、租约 + 看门狗、FIFO 公平等待、SB3 Starter | 无                                 | 6 个 Maven 模块 + README/Javadoc                | 概要设计 §4.3 四条成功标准全部通过 |
| **Phase 2（集群）** | 3/5 节点 Raft 高可用集群                                                  | Phase 1 完成                       | 集群化 server、客户端 Leader 发现、快照恢复     | §5.2 Phase 2 验收清单全部通过      |
| **Phase 3（平台）** | 功能完整：扩展锁类型、监控、控制台、安全                                  | Phase 2 完成（其中 T1 可提前并行） | FairLock/Semaphore/CDL、指标、控制台、TLS/Token | §5.3 Phase 3 验收清单全部通过      |

各阶段独立可交付：Phase 1 完成即可投产（单机场景）；阶段之间不交叉开发，避免接口未稳定导致的返工。

### 3.2 Phase 1 里程碑细分（M1–M4）

依赖关系：`M1 → M2 → M3 → M4`（严格串行，每个里程碑的验证是下一个的前置条件）。

#### M1：协议与纯 Java 核心（openlatch-protocol + openlatch-core）

- **目标**：完成 `.proto` 协议定义与锁语义核心。核心模块不依赖 Netty，全部正确性语义在此阶段以单元测试闭环验证——对应概要设计 §4.2"90% 正确性测试无需网络"与 §11 风险 5 的应对策略。
- **交付物**：
    - `openlatch-protocol`：Envelope/请求/响应/通知消息、错误码枚举、编解码；
    - `openlatch-core`：锁状态机（互斥/可重入/读写/限时）、FIFO 等待队列、租约表与会话表、到期扫描器；
    - 覆盖概要设计 §4.3 语义项的全部单元测试。
- **验证方式**：`mvn test`，core 单元测试全绿；语义用例清单见 §5.1 及《Phase1-详细设计说明书》§10。
- **退出标准**：互斥、重入计数、读写交错、FIFO 公平、租约到期释放、误释放拒绝、会话清理 7 类语义测试全部通过，无跳过用例。

#### M2：单节点服务器（openlatch-server）

- **目标**：Netty 接入层 + 请求分发 + 会话管理，把 M1 的核心暴露为真实网络服务；可执行 jar 可独立启动。
- **交付物**：服务端 pipeline（分帧/编解码/空闲检测）、请求分发器、会话生命周期管理、断连清理、服务端自我保护（限流/限额）、配置文件加载。
- **验证方式**：
    - 协议测试：Protobuf round-trip、未知消息类型处理（概要设计 §8）；
    - `EmbeddedChannel` 测试：半包/粘包、断连事件触发清理；
    - 冒烟测试：测试客户端完成 HELLO → ACQUIRE → RENEW → RELEASE 全链路。
- **退出标准**：单节点可稳定服务测试客户端；断连清理与限额保护有对应自动化用例通过。

#### M3：客户端 SDK（openlatch-client）

- **目标**：异步内核 + 同步包装 + 看门狗 + 断线重连，完成端到端可用系统。
- **交付物**：`OpenLatchClient` / `OLock` API、请求多路复用（requestId ↔ CompletableFuture）、等待通知跟踪、看门狗续租、指数退避重连、锁丢失回调。
- **验证方式**：
    - 集成测试：真实单节点 + 多线程客户端并发竞争（互斥断言）；
    - 故障注入：持锁中断连、等待中断连、杀服务端进程（概要设计 §8）；
    - 超时审计：代码评审 + 测试确认所有请求路径带超时，无死等。
- **退出标准**：概要设计 §4.3 标准 1–3 全部通过（故障注入与超时路径在客户端集成后才能真正端到端验证）。

#### M4：Starter、示例与文档（openlatch-spring-boot-starter + openlatch-examples）

- **目标**：Spring Boot 3.2+ 应用仅添加依赖与注解即可使用；补齐文档。
- **交付物**：自动装配（`AutoConfiguration.imports`）、`@OpenLatch` 注解 + AOP 切面（key 支持 SpEL）、examples 模块（基础用法/并发竞争/注解用法/基准测试）、README 与 Javadoc。
- **验证方式**：
    - Starter 集成测试：内嵌 Spring Boot 3.2+ 上下文，注解方法被互斥执行、SpEL key 按参数求值；
    - 基准测试：单节点 `tryLock` 吞吐与授予延迟基线（概要设计 §4.2，非发布门槛，仅记录基线防退化）；
    - 人工验收：按 README 从零接入一个示例应用。
- **退出标准**：概要设计 §4.3 标准 4 通过；四条成功标准全部闭环，Phase 1 发布。

### 3.3 Phase 2 步骤细分（S1–S4）

依赖关系：`S1 → S2 → S3 → S4`（S3 与 S2 后期可部分并行）。

| 步骤                               | 目标                                              | 交付物                                                                                  | 验证方式                                                                                      |
|------------------------------------|---------------------------------------------------|-----------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------|
| **S1 Raft 选型 PoC**               | 在 Apache Ratis 与 SOFAJRaft 之间做出有依据的选型 | PoC 代码（两库各实现最小锁状态机）、选型评估报告（并入《Phase2-详细设计说明书》修订版） | PoC 对比维度见《Phase2-详细设计说明书》§2：性能、快照、Netty 集成方式、API 契合度、社区活跃度 |
| **S2 复制状态机**                  | 锁状态经 Raft 日志复制到多数派                    | 日志条目定义、状态机接入（复用 openlatch-core）、Leader 上提供一致写                    | 日志序列回放确定性测试；3 节点集成：写入经 Leader、多数派确认后才响应                         |
| **S3 Leader 发现与客户端故障转移** | 客户端自动发现 Leader，切换后恢复服务             | 协议扩展（NOT_LEADER/leaderHint）、种子节点列表、客户端重连策略                         | 杀 Leader 演练：新 Leader 选出后客户端自动恢复，端到端 < 10s                                  |
| **S4 快照与恢复、容错加固**        | 节点重启/加入时从快照恢复；完成全部容错演练       | 快照序列化与加载、成员变更流程、故障演练套件                                            | §5.2 验收清单全部通过（含分区、滚动重启）                                                     |

## 4. 阶段间依赖与顺序约束

```
M1(协议+core) ──▶ M2(server) ──▶ M3(client) ──▶ M4(starter/examples)
                                                    │
                                              Phase 1 发布
                                                    │
                     S1(选型PoC) ─▶ S2(复制) ─▶ S3(故障转移) ─▶ S4(快照/加固)
                                                    │
                                              Phase 2 发布
                                                    │
                     T1(扩展锁) ─┬─▶ T3(控制台)     │
                     T2(指标) ───┘      T4(安全) ───┴─▶ Phase 3 发布
```

- Phase 2 依赖 Phase 1 的协议版本字段与 `NOT_LEADER` 预留错误码；
- Phase 3 的 T1 在语义上只依赖 core，可与 Phase 2 并行开发，但 **合入与发布**安排在 Phase 2 之后，避免集群语义未定时扩展锁类型引入返工；
- 每个里程碑结束时执行一次"回归全量测试"，保证后续阶段不破坏既有语义。

## 5. 验证体系

### 5.1 测试金字塔与职责（对应概要设计 §8）

| 层次     | 模块                 | 职责                                                                                            | 运行成本                        | 占比目标 |
|----------|----------------------|-------------------------------------------------------------------------------------------------|---------------------------------|----------|
| 单元测试 | `openlatch-core`     | 全部锁语义正确性：互斥、重入计数、读写交错、租约到期、FIFO 公平、误释放拒绝、会话清理、幂等去重 | 极低（纯 Java，无网络，毫秒级） | ~70%     |
| 协议测试 | `openlatch-protocol` | 编解码 round-trip、未知类型/字段容忍、版本字段                                                  | 极低                            | ~10%     |
| 集成测试 | server + client      | 真实进程/线程下的端到端行为：并发竞争、等待通知、看门狗续租                                     | 中（秒级）                      | ~15%     |
| 故障注入 | 全链路               | 持锁断连、等待断连、杀进程、（Phase 2）杀 Leader/分区                                           | 高                              | ~5%      |
| 基准测试 | examples             | 吞吐与延迟基线，防退化，**不作为发布门槛**                                                      | 高                              | 按需     |

原则： **先在 core 层证明语义正确，再接入网络**（概要设计 §11 风险 5）。集成/故障注入测试只验证"网络与集成没有破坏语义"，不重复语义穷举。

### 5.2 Phase 2 验收清单

1. 3 节点集群正常服务：锁授予/释放经 Leader 与多数派确认；
2. 杀 Leader：选举完成、客户端自动故障转移，端到端恢复 < 10s；存活会话持有的锁不丢失；
3. 少数派分区不能授予或释放任何锁（防脑裂双主）；
4. 快照触发后重启节点，状态与集群一致；新节点可经快照 + 日志追赶加入；
5. 滚动重启 3 节点，服务不中断，已持有的锁（会话存活）不丢失；
6. 故障切换期间无死锁、无锁泄漏（租约兜底用例通过）；
7. 概要设计 §7"集群 Leader 切换"行为与文档声明一致（锁操作快速失败重试，文档如实声明 failover 后锁可能失效的情形）。

### 5.3 Phase 3 验收清单

1. FairLock：并发竞争下授予顺序与排队顺序一致（FIFO 保证显式化并有测试锁定）；
2. Semaphore：许可计数、超额等待、租约到期归还许可全部有测试；
3. CountDownLatch：countDown/await 语义、计数归零广播唤醒、一次性语义有测试；
4. 指标：指标清单（见《Phase3-详细设计说明书》§3）完整暴露，Prometheus 抓取成功；
5. 控制台：可列出锁、持有者、等待者、会话与核心指标（端到端冒烟通过）；
6. 安全：启用 TLS 后拒绝明文连接；错误/空 Token 的 HELLO 被拒绝并断开。

### 5.4 完成定义（Definition of Done）

一个里程碑/阶段"完成"，当且仅当：

1. 全部交付物已合入主干，`mvn verify` 全绿；
2. 该阶段验收清单逐项有对应的自动化用例或验收记录；
3. 无已知正确性缺陷（P0 缺陷清零；P1/P2 缺陷记录在案并有跟进计划）；
4. 文档同步：README、Javadoc（公开 API 全覆盖）、相关详细设计说明书的修订（如实现中产生的设计决策变更）；
5. 基准测试记录在案（与上一里程碑对比无显著退化，退化 > 20% 需说明原因）。

三个阶段共拆分为 **69 个子任务**（Phase 1：33 个；Phase 2：19 个；Phase 3：17 个）。每个子任务可独立交付、独立验证，编号稳定，用于进度跟踪。完整定义（内容与交付物、前置依赖、验证）见各详细设计说明书对应章节；此处为索引与验证点速查。
