## 1. 项目概述

OpenLatch 是一款基于 **Netty** 实现的通用 **分布式锁服务**。采用自研锁服务器架构，锁状态维护在服务器内存中，通过租约（Lease）机制与看门狗（Watchdog）自动续租保证锁的可靠释放；后续阶段通过 Raft 日志复制实现多节点集群化。客户端以轻量 Java SDK 与 Spring Boot Starter 两种形态接入。

一句话定位： **不依赖 Redis/ZooKeeper 等中间件、开箱即用的轻量级分布式锁服务。**

## 2. 项目背景

### 2.1 前身：EasyLock

作者于 2021 年实现了 EasyLock 项目（`io.github.lamtong:easylock`，四模块：common / client / server / spring-boot-starter，54 个 Java 文件，版本演进至 1.3.2），基于 Netty + Protobuf 实现了"锁服务器 + 客户端"模式的分布式锁，支持 SimpleLock、TimeoutLock、ReentrantLock、ReadWriteLock 四种锁及注解式用法，但项目随后中止。

### 2.2 现状分析：已实现的部分

- 四模块 Maven 工程结构清晰，客户端-服务器职责分离
- Protobuf 协议承载加锁/解锁请求与响应
- 客户端通过 `FixedChannelPool` 连接池与限流队列发送请求
- 服务端按锁类型分发请求，阻塞式 `lock()` 由每 key 一条队列串行化处理
- Spring Boot 2 Starter 提供 `@BySimpleLock` 等四个注解 + AOP 切面

### 2.3 现状分析：存在的问题

**正确性缺陷：**

| # | 问题                                                                                                               | 位置                               |
|---|--------------------------------------------------------------------------------------------------------------------|------------------------------------|
| 1 | `unlock()` 无条件 `remove(key)`，任何客户端都能解开别人的锁                                                        | `SimpleLockResolver#resolveUnlock` |
| 2 | `ResponsePool` 响应可能先于队列注册到达，靠 `while(!containsKey)` 空转自旋；客户端 `take()` 无超时，断连后永久阻塞 | `ResponsePool` / `RequestSender`   |
| 3 | 阻塞等待管线 `poll(1s)→remove(key)` 与并发 `put` 存在竞态，可能丢失请求                                            | `DefaultPipeline`                  |
| 4 | 持锁客户端崩溃后，`SimpleLock` 无 TTL，锁在服务端永久持有                                                          | 协议层缺少租约                     |
| 5 | 服务端检测到连接断开只记日志，不清理该连接持有的锁                                                                 | `ServerHandler#channelInactive`    |

**架构缺陷：**

| # | 问题                                                                                 |
|---|--------------------------------------------------------------------------------------|
| 6 | 单节点、纯内存，无高可用、无持久化、重启即丢锁                                       |
| 7 | 阻塞式 `lock()` 在服务端为每个等待者占用一个线程（无界线程池），扩展性差             |
| 8 | 客户端单地址配置，无重连、无故障转移；自动连接靠对 `_auto_connect` key 加解锁的 hack |
| 9 | 无看门狗续租、无公平等待、无 `tryLock(timeout)`、无认证、无监控                      |

**工程缺陷：**

| #  | 问题                                                                           |
|----|--------------------------------------------------------------------------------|
| 10 | 零测试用例                                                                     |
| 11 | 依赖过时：Netty 4.1.6、Spring Boot 2.5.2、Java 8；Starter 不兼容 Spring Boot 3 |
| 12 | 注解 key 只支持字面量常量，不支持表达式                                        |

上述问题构成重启该项目的直接动因：在保留"基于 Netty 的自研锁服务"这一核心价值的前提下，全新重写，修复全部正确性缺陷，并向成熟产品的功能完整度看齐。

## 3. 项目意义

1. **去除中间件依赖**：中小项目获得分布式锁能力，无需为此运维 Redis / ZooKeeper / etcd 集群；部署一组（最少单节点）OpenLatch 服务器即可。
2. **语义完整**：不止 setNx 式互斥，提供可重入、读写锁、公平等待、看门狗续租等 JUC Lock 风格的完整语义。
3. **正确性优先**：以租约 + 会话双保险机制从设计上消灭锁泄漏、死锁、误释放三类分布式锁经典事故。
4. **工程示范价值**：完整覆盖自定义协议设计、长连接会话管理、异步内核、一致性与容灾等主题，是 Netty 服务端编程的完整案例。

## 4. 项目目标

### 4.1 功能目标

| 优先级 | 功能                                                    | 阶段    |
|--------|---------------------------------------------------------|---------|
| P0     | 互斥锁、可重入锁、读写锁、限时锁（`tryLock(waitTime)`） | Phase 1 |
| P0     | 租约 + 看门狗自动续租，锁不泄漏                         | Phase 1 |
| P0     | 服务器端 FIFO 公平等待，无惊群                          | Phase 1 |
| P0     | Spring Boot 3 Starter：注解式加锁，key 支持 SpEL        | Phase 1 |
| P1     | 多节点集群：Raft 复制、Leader 切换、快照恢复            | Phase 2 |
| P2     | FairLock 显式化、Semaphore、CountDownLatch              | Phase 3 |
| P2     | 监控指标（Micrometer）与管理控制台、TLS/Token 认证      | Phase 3 |

### 4.2 非功能目标

- **可靠性**：客户端崩溃后，锁在一个租约期内必然自动释放；任何 API 不存在无限阻塞路径
- **性能**（单机基线）：`tryLock` 吞吐 ≥ 10,000 ops/s（本地环境参考基线）；锁授予延迟 P99 < 5ms（本机回环）
- **可用性**：客户端断线自动重连（指数退避）；服务端连接断开即时清理相关锁状态
- **可维护性**：锁语义核心独立为纯 Java 模块，90% 正确性测试无需网络

### 4.3 成功标准（可验证）

1. 互斥、重入计数、读写互斥、FIFO 公平、租约到期释放——全部有自动化测试覆盖
2. 故障注入测试通过：持锁中断连 → 租约到期后锁自动释放；等待中断连 → 快速失败
3. 客户端所有请求路径带超时，无死等用例
4. Spring Boot 3.2+ 应用仅添加依赖与注解即可使用

## 6. 核心机制设计

### 6.1 协议设计

长连接双向通道，所有消息携带连接内唯一的 `requestId`（long），响应与推送均按 `requestId` / `sessionId` 关联。

```
客户端 ── 请求 ──▶ 服务器       LOCK_ACQUIRE / LOCK_RELEASE / LEASE_RENEW / PING
客户端 ◀── 响应 ── 服务器       按 requestId 关联，含错误码与原因
客户端 ◀── 通知 ── 服务器       AWAIT_NOTIFY：等待队列前进时主动推送
```

消息类型以 proto `enum` 定义（替代前身的魔法数字 `type` 字段）。协议包含版本字段，为 Phase 2 集群语义（Leader 重定向等）预留扩展。

### 6.2 锁获取与等待模型

取代前身"服务端每等待者一个阻塞线程"的模型：

```
客户端 lock(key)
  → 发送 LOCK_ACQUIRE（lockType / reentrant / lease 时长）
  → 服务器判定：
      锁空闲            → 授予锁，响应 success + leaseToken
      锁被占            → 登记到该 key 的 FIFO 等待队列，响应 QUEUED
  → 客户端在本地 CompletableFuture 上挂起（受用户指定总超时约束）
  → 持锁者释放 → 服务器向队首推送 AWAIT_NOTIFY → 队首重发 ACQUIRE → 授予
```

要点：

- 服务器 **不为等待者挂起任何线程**，等待者只是内存队列中的条目，扩展性不再受线程数限制
- 等待队列维护在服务器端， **公平性由服务器保证**，且只唤醒队首，无惊群
- 等待者断连或超时 → 自动移出队列；不影响其他等待者

### 6.3 租约与看门狗

- 每次授予锁附带 **lease（默认 30s）** 与 **leaseToken**
- 客户端持锁期间，后台定时器每 `lease/3` 发送 `LEASE_RENEW`
- 续租失败（锁已被抢占/服务器不可达/超时）→ 锁标记失效，触发用户注册的"锁丢失"回调
- 服务器端硬到期：租约到期未续租 → 自动释放并唤醒队首
- `unlock()` 必须携带 leaseToken，服务器校验归属，不匹配则拒绝（修复前身"任意客户端可解锁"缺陷）
- 不续租的锁必然释放——以机制代替人工清理

### 6.4 会话管理

- 客户端建连后由服务器分配 **sessionId**；锁归属记为 `(sessionId, threadId)`
- 连接断开 → 服务器立即清理该 session 持有的全部锁与等待项
- 锁生命周期双保险： **连接级清理（即时）+ 租约级过期（兜底）**
- 重连后为新 session，旧锁已失效——客户端语义明确："断线超时即失锁"，由应用层决定补偿

### 6.5 锁类型（Phase 1 范围）

| 类型            | 语义                                                      |
|-----------------|-----------------------------------------------------------|
| `ReentrantLock` | 同 `(session, thread)` 可重复获取，按计数释放（默认类型） |
| `SimpleLock`    | 不可重入的一次性互斥锁                                    |
| `ReadWriteLock` | 读锁共享计数、写锁互斥，读写互斥                          |
| `TimedLock`     | `tryLock(waitTime, unit)` 限时等待                        |

Phase 3 扩展：FairLock（MVP 的 FIFO 队列已天然公平，届时提供显式类型）、Semaphore、CountDownLatch。

### 6.6 客户端 API

异步内核是一切的基础，同步 API 为包装：

```java
// 异步内核
CompletableFuture<LockGrant> acquireAsync(LockRequest request);

// 同步包装（JUC 风格）
OLock lock = client.newReentrantLock("order:123");
lock.

lock();                          // 阻塞，受总超时兜底
lock.

tryLock(5,TimeUnit.SECONDS);    // 限时等待
lock.

unlock();

// Spring Boot 注解
@OpenLatch(key = "'order:' + #orderId", waitTime = 3, leaseTime = 30)
public void fulfillOrder(String orderId) { ...}
```

注解 key 支持 SpEL 表达式（前身为字面量常量，属明显短板）。

## 7. 可靠性与错误处理

| 故障场景                    | 行为                                                                                                                |
|-----------------------------|---------------------------------------------------------------------------------------------------------------------|
| 请求超时                    | 客户端每个请求带超时；传输层空闲检测兜底；无无限阻塞路径                                                            |
| 断连（持锁中）              | 客户端指数退避重连；断连超过一个租约期后锁在服务端失效，客户端触发"锁丢失"回调                                      |
| 断连（等待中）              | 等待项随 session 清理；客户端快速失败，可重试                                                                       |
| 服务器重启（单机）          | 锁状态丢失 = 全部锁释放；租约保证不会残留假锁                                                                       |
| 误释放                      | `unlock()` 校验 leaseToken，不匹配拒绝                                                                              |
| 重复请求                    | 按 `(sessionId, requestId)` 幂等，重复 ACQUIRE 不二次排队                                                           |
| 服务器自我保护              | key 长度、单连接并发请求数、等待队列深度设上限，超限返回明确错误码                                                  |
| 集群 Leader 切换（Phase 2） | 锁操作快速失败重试；客户端从种子节点自动发现新 Leader；failover 后锁可能失效（与 Redis 主从切换同理，文档如实声明） |
